# ADR 0020: Text Extraction (PDF, DOCX, Markdown and Text) and Its Sandbox

**Status:** Accepted (libraries and sandbox). The implementation plan follows in Session 4, Step 4.

**Date:** 2026-10-23

**Deciders:** Hamza Asif

## Context

Session 4, Step 4 turns an uploaded file into text that Step 5 can split into chunks. The output must keep section numbers (for example `4.2.3`) and headings, so that answers can cite a section (SPEC §6.2). Extraction reads untrusted files, so it must be bounded in time and memory and must not leak data through the XML it parses (SPEC §6.1, ADR 0019).

## Decisions

### 1. Libraries

| Format | Chosen | Licence (checked on PyPI and in installed metadata) | Why |
|---|---|---|---|
| PDF | **pypdf** 6.21.2 | BSD-3-Clause | Best text match and table fidelity of the PDF libraries measured; font sizes available for heading levels; has its own decompression limit |
| DOCX | **python-docx** 1.2.0 | MIT | Exact match on the demo set; walks the body in order; keeps heading styles and tables |
| Markdown, text | **markdown-it-py** 4.2.0 | MIT (with `mdurl` 0.1.2, MIT) | Keeps heading levels and table cells from the token stream |
| Packaging dependency (of python-docx) | lxml 6.1.3 | BSD-3-Clause | Parser for the XML inside the DOCX; see decision 4 |

**Rejected, with reasons:**
- **PyMuPDF** (AGPL-3.0 or commercial): the AGPL requires a network service that runs a modified version to offer its source to users. For a multi-tenant web service that is an obligation we do not accept, and the commercial licence is a paid alternative.
- **pdfplumber** (MIT): recovered 382 of 441 table cells, against 434 for pypdf. Its text match was 0.987.
- **pdfminer.six** (MIT): text match 0.957, the lowest. It reports one extra empty page at the end of each file.
- **pypdfium2** (BSD-3-Clause, Apache-2.0): fastest (0.3 s for the set), with table and page results equal to pypdf's. It does not expose font sizes in version 5.14.0, so it cannot tell heading levels apart. On the decompression bomb it reached the 2 GB ceiling in 11 s.
- **mammoth** (BSD-2-Clause): equal text quality, but the markdown it produces puts an HTML anchor in every heading and escapes punctuation. Without that cleanup, heading detection scores 0 of 60.
- **docx2python** (MIT): equal to python-docx on this set. Kept as the fallback if python-docx ever fails.

### 2. Measured results

Ground truth: the Markdown source of each demo document (`demo-data/indus-freight/source/`). The uploaded files were produced from those sources. Scoring is per library over all matching files.

**PDF (3 files, 31 section numbers, 34 headings, 441 table cells):**

| Library | Text match | Section numbers | Headings (own line) | Table cells | Pages | Speed (3 files) | Font size available |
|---|---|---|---|---|---|---|---|
| pypdf 6.21.2 | 0.997 | 31/31 | 34/34 | 434/441 | 3/3 | 1.9 s | yes |
| pdfplumber 0.11.10 | 0.987 | 31/31 | 34/34 | 382/441 | 3/3 | 4.6 s | yes |
| pdfminer.six 20260107 | 0.957 | 31/31 | 34/34 | 434/441 | 3/3 | 3.0 s | yes |
| pypdfium2 5.14.0 | 0.997 | 31/31 | 34/34 | 434/441 | 3/3 | 0.3 s | no |

**DOCX (4 files, 56 section numbers, 60 headings, 493 table cells):**

| Library | Text match | Section numbers | Headings (own line) | Table cells | Speed |
|---|---|---|---|---|---|
| python-docx 1.2.0 | 1.000 | 56/56 | 60/60 | 493/493 | 0.6 s |
| docx2python 3.7.1 | 1.000 | 56/56 | 60/60 | 493/493 | 0.7 s |
| mammoth 1.13.0, raw | 0.989 | 56/56 | 0/60 | 493/493 | 0.6 s |
| mammoth 1.13.0, anchors and escapes removed | 1.000 | 56/56 | 60/60 | 493/493 | 0.7 s |

**Markdown (1 file, 13 section numbers, 14 headings, 125 table cells):** markdown-it-py gives 1.000, 13/13, 14/14 and 125/125. The plain-read baseline matches on text but keeps no structure.

**Pages:** PDF pages come back separately from pypdf, pdfplumber, pdfminer.six and pypdfium2. DOCX has no pages, so `page` is null for DOCX.

**Caveats of the measurement:**
- Text match is a word-sequence ratio. It shows reading order and completeness, not visual layout.
- Heading "own line" means the title appears on a line of its own, and that line contains the section number where the source has one.
- The demo set is generated by the owner. It is not a sample of real-world files.

### 3. Hostile-file measurements

Each file was run in its own child process, with a 60-second timeout and a 2 GB memory monitor on the whole process tree.

| File | pypdf | pdfplumber | pdfminer.six | pypdfium2 |
|---|---|---|---|---|
| Decompression bomb: 143 KB, about 100 MB inflated | Refused in 1 s, 111 MB, by its own decompression limit | Killed at 60 s, 1.2 GB | Killed at 60 s, 1.2 GB | Killed at 2 GB after 11 s |
| Deep nesting: 100k nested arrays, 50k nested dictionaries | **Killed at 60 s** | Returned in 1.5 s, no text | Returned in 1.8 s, no text | Returned in 0.6 s, no text |
| Garbage after a valid header: 2 MB | Clean error in 1 s | Clean error in 0.7 s | Clean error in 0.7 s | Clean error in 0.7 s |

Conclusion: no library bounds its own time or memory on hostile input. Limits must come from outside the library.

### 4. DOCX XML security: verified

Entities are not resolved in DOCX XML, and the check is both source-level and behavioural.

- **Source (python-docx 1.2.0):** both parsers set `resolve_entities=False`. One is in `docx/oxml/parser.py`, used for the document part. The other is in `docx/opc/oxml.py`, used for the packaging parts (content types, relationships, and the parts read by the package reader).
- **Behaviour (scratch test, with a canary file containing a known secret):**
  - An external entity (XXE) pointing at the canary: python-docx returns the text with the entity dropped. The secret does not appear.
  - A billion-laughs payload (about 3 GB if expanded): lxml refuses the document with `XMLSyntaxError`. Nothing expands.
  - Control: the same XXE payload parsed with a default lxml parser (`resolve_entities=True`) does leak the canary. So the test detects a leak when one happens.
- **Requirement for Step 4:** the test for both payloads is kept in the suite. A python-docx upgrade must not change the result.
- **Note:** the `XMLSyntaxError` for the billion-laughs file must be mapped to a clean ingestion failure in Step 6, not to a 500.

### 5. Sandbox: child process, limits per platform

- Every extraction runs in a child process (`python -I`). The bytes go in on stdin, and the structure comes back as JSON on stdout. Nothing is written to disk.
- **Timeout (all platforms, including Windows):** the parent kills the child and its children after the limit. Proposed limits: 30 s for PDF, 10 s for DOCX, 5 s for Markdown and text.
- **Memory (Linux only, production and CI):** the child sets `RLIMIT_AS` with the `resource` module before it imports the parser. Proposed ceiling: 1 GiB of address space. An allocation past the limit fails in the child.
- **Windows (development):** timeout only. A hard memory limit on Windows needs a Job Object, which the stdlib does not provide and which we do not add as a dependency. This is documented as a limit of development on Windows, not of production.
- **Output cap:** the parent refuses child output above 50 MiB, so a bomb cannot push a large result into the parent either.
- **Proof in CI:** a test runs the decompression bomb in the child with the memory limit, and asserts that the child is killed or fails, that no structure comes back, and that the parent stays up. It runs on the Linux CI job. On Windows it is skipped with the reason "RLIMIT_AS is Linux-only; this test runs in CI". That skip is the only one allowed for it.

### 6. One structure for every format

Extraction returns the same structure whatever the format, for Step 5 to chunk:

- `Extracted`: format, page count (null when the format has no pages), and a tuple of sections.
- `Section`: number (for example `"4.2.3"`, or null), heading text, level, page (PDF only, otherwise null), body text, and tables.
- `Table`: rows of cell text.

Heading level comes from the format: heading styles for DOCX, the heading tokens for Markdown, and font size for PDF.

## Consequences

- **Positive:** the libraries are permissive, and the measured quality is high on the demo set. The sandbox bounds the damage a hostile file can do, on every platform, and proves the memory bound in CI.
- **Negative:** the sandbox adds a process per extraction, and a few hundred milliseconds of start-up. Acceptable at our volume.
- **Negative:** the Windows memory limit is not enforced. Development on Windows is therefore less protected than production. The gap is recorded in SECURITY.md.
- **Negative:** heading levels in PDF depend on font sizes. A PDF with unusual styling may get levels wrong. The measured set is good; real files may not be.

## Decisions from the review (2026-10-23)

- **D-A: tables as text in v1 (pypdf, no table structure for PDF).** If the Session 5 evaluation shows that PDF table questions fail, this decision is revisited with that evidence, and pdfplumber is the first candidate to add.
- **D-B: hybrid heading detection for PDF.** Font size identifies heading lines: a line in a font larger than the body size and short enough to be a title. The **level** comes from the numbering when present (the dots in `4.2.3` give level 3). Font size sets the level only for unnumbered headings, such as a document title.
- **D-C: scanned PDFs are refused with "no text found".** OCR is out of scope for v1. SPEC.md gets the limitation (wording approved in the review diff).
- **D-D: limits accepted.** Timeouts: 30 s PDF, 10 s DOCX, 5 s Markdown and text. Memory: 1 GiB address space on Linux. Output: 50 MiB. The 1 GiB value is checked on the demo set before it is relied on.
- **Child-process stderr is never logged or returned.** A traceback from a child process can carry document text. Every failure maps to one of four generic reasons (`timeout`, `memory`, `unreadable`, `no_text`). The log records at most the exception type and the length of the message. A test puts a unique marker in a document that makes the child fail, and asserts that the marker appears in neither the logs nor the failure reason.

## Implementation findings (2026-10-23)

- **Linux results (Docker, python:3.12-slim, locked dependencies):** the extraction tests pass, 45 of 46. The one skipped test is the Windows-only check. All eight demo files extract under the 1 GiB limit, in 0.7 to 1.4 s each.
- **The body size is the smaller size on a tie.** Body size is the font size covering the most characters. On a tie the smaller size wins, since body text is smaller than headings. Without this, insertion order decided, and a title could be read as body text.
- **pypdf's limits differ from what the first measurement suggested.** The deep-nesting file that hung for more than a minute in the measurement now raises `RecursionError` at once in the same environment, and I did not reproduce the hang. The timeout is therefore proven two ways: a child that sleeps is stopped at 2 s (every platform), and the real deep-nesting file ends as timeout or unreadable within a bound.
- **pypdf refuses the real bomb itself** (`LimitReachedError` after about 111 MB). The Linux memory limit is proven with a stdlib-only decompression bomb under a 256 MiB limit, because it is the limit that has to stop the bomb in that test.
- **Lint suppressions for the sandbox's subprocess calls** (ruff rule S603): two call sites carry `noqa` with a stated reason, because the arguments are fixed and the file is never on the command line. Approval is requested in the review; see the PR description.

## Amendment (ADR 0022, 2026-10-23): a fifth reason

The ingestion worker adds two reasons (ADR 0022). `embedding`: the embedding model failed on the document's text. `retries_exhausted`: every attempt hit a transient error. The reason list is now `timeout`, `memory`, `unreadable`, `no_text`, `embedding` and `retries_exhausted`. The last two are not extraction reasons, but they are generic, so an admin can tell a bad document from an outage. The stderr rule is unchanged. The model's error message is never stored or logged, only its exception class name.
